# Публичная витрина: насколько ей можно верить и как сделать честно

Статус: предложение, в коде пока ничего не менялось. Связано с этапом P0 «Серверно-авторитетная экономика» в `docs/jarvis-roadmap.md`.

## Как устроено сейчас (`server/worker.js`)

1. Игрок выбирает 3 карточки. Выбор хранится в `social_profiles.data.showcase`, это только пожелание.
2. При изменении витрины и при каждом сохранении (`/save` → `reverifyOnSave`) сервер вызывает `verifyShowcase`. Тот проверяет, что у игрока есть свободная копия: `cards.own − cards.used ≥ 1` в **сохранении, которое прислал клиент**.
3. Для особых карточек (`FL:*`, «Забытые легенды») дополнительно нужна серверная запись о выдаче в `legend_claims`.
4. Другие игроки видят только результат проверки из `social_shown`.

## Что это гарантирует и что нет

| Карточки | Есть ли серверная запись о выдаче | Можно ли подделать |
|---|---|---|
| `FL:*` | да, `legend_claims` (однократная выдача сервером) | нет |
| Обычные (бронза…Джексон, «Будущие звёзды») | нет: паки открываются на клиенте, а `purchases`/`payment_receipts` знают только *что* куплено, не *какие* карточки выпали | да |

Как подделывают: модифицированный клиент шлёт `/save` с `cards.own: {"<любая карточка>": 1}`, сервер принимает её как «найденную в сохранении», и она появляется в публичной витрине. Экономической выгоды подделка не даёт: витрина ничего не начисляет, а ИПК и обмен по-прежнему клиентские. Но получается фальшивое «хвастовство», и это подрывает доверие к профилю.

## Предложение

### Шаг 0. Сразу, без изменений экономики (нужно ваше решение)
Выберите один вариант:

- **А (рекомендую). Честная подпись.**
  - Карточки с серверной записью (`FL:*`, позже — всё из журнала) получают значок «✓ подтверждено сервером».
  - Остальные показываются с пометкой «по данным сохранения».
  - Это одна строка в ответе профиля (`verified: [true,false,…]`) и значок в `Social.layout`. Витрина не пустеет.
- **Б. Строгий режим.** Публично показываются только подтверждённые сервером карточки. Остальные видит только владелец. Честно, но до перехода на серверную экономику витрины у почти всех будут пустыми.

В обоих вариантах стоит добавить модерацию через существующую таблицу `reports`: админ скрывает витрину игрока (`social_shown` → пусто) по жалобе.

### Шаг 1. Журнал выдачи (часть P0, вместе с переходом экономики)
- Таблица `inventory_ledger(uid, card, delta, reason, action_id UNIQUE, created)`.
- Паки открывает сервер. Он выбирает карточки серверным генератором случайных чисел по тем же шансам: **шансы и состав паков не меняются, меняется только место броска**. Каждая выдача пишется в журнал идемпотентно по `action_id`; для покупок за Stars это `payment_receipts.charge`.
- Сдача в ИПК и подарки в клубе пишут отрицательные записи в одной транзакции D1.
- `verifyShowcase` проверяет баланс по журналу (`SUM(delta) ≥ 1`), а не клиентское сохранение.

### Шаг 2. Старые коллекции (миграция без потерь)
- В день перехода текущее серверное сохранение каждого игрока фиксируется в журнал как `reason='legacy'`. У игроков ничего не отнимается.
- После этой даты новые карточки принимаются только через журнал. Подделать «старую» карточку задним числом нельзя, потому что снимок заморожен.
- Карточки из `legacy` можно показывать со спокойной пометкой «из коллекции до обновления», пока они не будут подтверждены. Для явно неправдоподобных снимков (например, все карточки «Джексон» у аккаунта возрастом в день) снимок помечается к ручной проверке.

### Шаг 3. Проверки
- Повтор `action_id` не удваивает карточку.
- Обрыв сети посередине открытия пака не даёт ни потери, ни дубля.
- Одновременные подарки в клубе не уводят баланс ниже нуля.
- Подделанный `/save` с лишними карточками не меняет `social_shown`.

## Стоимость в D1
- Шаг 0: ноль новых запросов. Проверка уже есть, к ответу добавляется только флаг.
- Шаг 1: +1 запись на каждую выданную карточку. Проверка витрины — 3 чтения `SUM` по индексу `(uid, card)` при сохранении, не при просмотре.
