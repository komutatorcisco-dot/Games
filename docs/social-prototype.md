# Социальные функции — поэтапное включение

Подготовлено в `codex/social-collection`, перед выпуском перенесено поверх `acbd4ca`. Пользователь разрешил публикацию 14 октября с проверкой нагрузки. Награды, цены, шансы паков, характеристики и оформление самих карточек не менялись.

## 1. Избранное и защита ИПК

Сердечко находится отдельно под карточкой галереи. Отметить можно карточку с доступной копией; историческая запись о сданной карточке владением не считается. Есть фильтр избранного.

`Social.available(key) = max(0, Cards.spare(key) - favorite)`; сохранение одной копии применяется к автосбору, сохранённым позициям автосбора, ручному подтверждению и непосредственно к `Cards.use`. Списание набора предварительно проверяет все количества, включая повтор одного ключа; при ошибке не списывает ничего. ИПК повторно проверяет защиту после синхронизации и не начисляет награду при отказе. Дополнительные копии можно сдавать. Последнюю можно сдать после снятия отметки.

Это защита интерфейса от случайной сдачи, не новая серверная экономика. В текущей основной ветке ИПК и основной инвентарь по-прежнему клиентские. Модифицированный клиент может обходить эти ограничения до подключения авторитетного списания из этапов экономики.

## 2. Личная витрина

Три места в существующем профиле, замена через поиск/постраничный выбор (18 карточек на страницу), перестановка стрелкой, удаление крестиком. Используется существующий `Cards.html`. Сданная последняя копия немедленно скрывается из активной витрины; историческая галерея сохраняется.

Настройки хранятся отдельно от экономического сохранения в таблице `social_profiles` с ревизией. `POST /social` проходит существующую проверку Telegram initData. Собственный uid берётся только из проверенной сессии, поля клиента не используются для выбора владельца.

Backend включён по умолчанию; аварийное отключение — `SOCIAL_ENABLED=0`. Создание отдельной таблицы настроек идемпотентно, старые таблицы не изменяются. Публичные карточки остаются выключенными независимо от переменной.

Сравнение ревизии при UPDATE предотвращает потерю изменений между устройствами. Очередь абсолютных операций сохраняется локально, повторяется после обрыва ответа и применяется поверх свежей ревизии. Очередь не копируется в старый облачный snapshot, чтобы другое устройство не переигрывало старые локальные команды. При восстановлении старого экономического сохранения локальная очередь social сохраняется отдельно.

Синхронизация происходит после начальной загрузки облака, изменений, возврата в приложение, появления сети и перед сдачей ИПК. При недоступности настроенного social endpoint сдача останавливается, чтобы не потерять защиту с другого устройства. При явном disabled endpoint остаётся локальная защита. Отключённый endpoint не блокирует прежний ИПК.

## Проверка нагрузки перед выпуском

- Быстрые изменения объединяются за 500 мс, до 100 операций в одном запросе. Одна пачка — один UPDATE с CAS; повтор без изменений не пишет в D1.
- Социальные изменения сохраняются локально без запуска старого облачного сохранения экономики.
- Возвраты в приложение ограничены одним чтением за 30 секунд. Перед ИПК чтение обязательное; постоянных таймеров опроса нет.
- Идентификаторы профилей кешируются на 60 секунд, максимум 512 записей на экземпляр Worker. Приватность не кешируется. На холодном Worker кеш начинается заново.
- Локальный SQLite-тест настоящего обработчика: 50 операций = 1 UPDATE + 2 SELECT; повтор = 0 UPDATE + 1 SELECT; 100 повторных поисков handles = 1 SELECT; 100 быстрых событий возврата клиента = 0 дополнительных запросов после синхронизации. Это не замер квот production D1; при первом входе создаётся одна строка профиля, индексы также учитываются в биллинге D1.
- Мобильные размеры 360/390/430 px проверены в Chrome. Выбор ограничен 18 карточками. 1000 повторных render без изменения данных заняли 1,4 мс на настольном Chrome с мобильным viewport; реальный телефон не измерялся. Неизменившаяся витрина не пересоздаёт DOM и изображения.

## 3. Публичные профили — частично, публичная витрина выключена

Приватность по умолчанию закрыта. Пользователь может открыть ник, игровой аватар-эмодзи, уровень по существующим порогам, трофеи и доступное серверное достижение «Игрок дня». Остальные достижения, которые пока вычисляются только локально, не выдаются за проверенные сервером. Статистика использует существующие серверные таблицы и сохраняет их прежние ограничения доверия к клиентским результатам.

Публичный endpoint возвращает только белый список полей. Он не возвращает Telegram ID, initData, полное сохранение, избранное, настройки или покупки. Для ссылок используется случайный 128-битный идентификатор. Ник/аватар экранируются в UI. Закрытие профиля действует сразу, ответы профиля не кешируются приложением.

Ссылки добавлены к никам рейтинга, участникам/чату клуба и сопернику онлайн-лобби. Связь с соперником проверяется по серверному членству в комнате, а не по имени/идентификатору, присланному другим клиентом. Профили доступны после регистрации social-настроек игроком. Существующий внутренний протокол клубного управления не переписывался.

Публичная витрина **всегда возвращает пустой список и `showcaseEnabled:false`**. Нельзя включить её переменной окружения или отправкой поддельного `cards.own`. Сохранённые ключи личной витрины не считаются доказательством владения. Нет импорта владения из `/save`, localStorage, параметров профиля или снимков клиента.

Для завершения этапа 3 нужен адаптер авторитетного инвентаря из PR №4–5: подтверждённые доступные количества с учётом списаний и миграционных статусов. Проверять выбранные три ключа при каждом публичном чтении; неизвестные/неперенесённые/нулевые остатки скрывать. Затем проверить на staging D1 и только после этого разрешить публичную витрину. Не включать по факту наличия legacy-сохранения на сервере. Read-only окно подробностей карточки уже подготовлено и не меняет локальные fresh/own/used.

- `node tests/social-browser.test.js` (Playwright): реальный Chrome с мобильным viewport 390×844, проверка ширин 360/390/430, избранное, фильтр, замена/перестановка/удаление, экранирование чужого ника. Используется явно отмеченная тестовая коллекция и fixture публичного профиля; тест не обращается к production API.
- `node tests/card-picker-browser.test.js`: существующие мобильные выборы карточек в составе и ИПК прошли.

Скриншоты: `tests/social-mobile-profile.png`, `tests/social-mobile-picker.png`, `tests/social-mobile-public.png`. Это Chrome с мобильными размерами, не замер на физическом iPhone. Просмотр: запустить статический сервер из корня репозитория, открыть `/tests/social-preview.html`. Прототип использует тестовые карточки, не настоящие награды. Для проверки реальной авторизации/синхронизации нужно отдельно согласовать запуск тестового Worker с SOCIAL_ENABLED=1 и тестовой D1. Рабочую конфигурацию не менять.
