### Ограничение
Флаг `broadcast:enabled` отключает маркетинговые массовые рассылки. Он не блокирует ответы на команды, сообщения поддержки и уведомления об успешной покупке. `/broadcast` остаётся синхронной задачей, поэтому для больших списков нужна очередь.

## Этап P0. Серверно-авторитетная экономика — НЕ ГОТОВ

### Проблема
Клиентские `xp`, `win`, `trophies` и факт владения карточками нельзя считать достаточным доказательством честной победы или передачи предмета.

### Последовательность миграции
1. Ввести версионированный журнал транзакций `inventory_ledger` (uid, item, delta, reason, unique_action_id, created).
2. Сохранять каждую покупку Stars и каждую награду от игры идемпотентно по уникальному ключу.
3. Постепенно мигрировать сохранения старых игроков: зафиксировать начальный остаток и пометить старые предметы как `legacy`, не отнимать купленное.
4. Для `/club don` списывать запасную карточку у дарителя и начислять её получателю в одной D1-транзакции. Нельзя послать несуществующую карточку или повторить один подарок.
5. Для драфта проверять результат серверным симулятором по зафиксированному seed/roster, а не доверять `state.over`.
6. До миграции отображать публичные лидерборды как предварительные; не выдавать новые дорогие призы на основе непроверенных результатов.
7. Тестировать повторные запросы, сбои сети, одновременные пожертвования и восстановление истории покупок.

Критерий готовности: пользователь не может создать карточку, трофеи или награду отправкой произвольного JSON; покупки сохраняются при любой повторной доставке webhook.

## Этап P1. Производительность — НЕ ГОТОВ

Базовая оценка по репозиторию: 94 локальных JS-скрипта ~3,1 МБ исходных данных + ~0,5 МБ CSS при открытии `index.html`. Это не сетевой замер: по HTTP файлы могут быть сжаты и закэшированы.

1. Добавить браузерные метрики cold/warm start для iPhone/Android, Slow 4G, FPS и Largest Contentful Paint.
2. Построить граф глобальных зависимостей классических JS-скриптов, иначе lazy-loading способен сломать игру.
3. Загрузить тяжёлые исторические базы (голы/матчи/рейтинги) только перед зависимыми викторинами.
4. После проверок перевести отдельные режимы на динамическую загрузку и провести тесты всех маршрутов.
5. Оптимизировать изображения, подготовить `loading=lazy`, `decoding=async`, preload только для первого экрана.
6. Следить за размером и числом запросов на главной странице в CI.

Критерий готовности: существенное снижение cold-start и отсутствие регрессий карточек, фото и онлайна.

2. Проверять GitHub Actions unit и Playwright браузерные тесты.
3. Делать резервную копию D1 до изменения схемы или инвентаря.
4. Подтверждать конфигурацию Telegram webhook и секретов перед публикацией.
5. Выпускать в production небольшими шагами с проверкой /start, оплаты, галереи, онлайна и /stop.
6. При регрессии откатить **только код** на предыдущий коммит; не откатывать D1 без отдельного плана миграции.
