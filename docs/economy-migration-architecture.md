# JARVIS — план безопасной миграции экономики на Cloudflare D1
Состояние: **архитектура и SQL-прототип, НЕ внедрено в production**. Дата: 2026-10-11.

## Проверенный исходный код
Ветка `claude/telegram-channel-games-kj1xly`, после выпуска PR #2.
- `js/core.js`: `Store.d.coins`, `Coins.add/spend` выполняются локально; `Cloud.pull` выбирает сохранение по трофеям и timestamp, без проверки ценных активов.
- `js/cards.js`: `cards.own` означает исторически полученные копии, `cards.used` — потраченные в SBC; свободных копий = own-used. `Cards.draw` и пакеты используют `Math.random` на клиенте.
- `js/rewards.js`: выдача `giveReward`, `claimRoad`, `claimPass` и `addTrophies` выполняется локально.
- `js/shopstars.js`: `grant` выдаёт пак/монеты на клиенте после подтверждения покупки. Клиентская отметка paid — не достаточная серверная защита; платёж Telegram подтверждает Worker.
- `js/clubs.js` + `server/worker.js`: `/club don` проверяет срок запроса/членство, но не проверяет серверный инвентарь донора и не списывает карту из него в D1.
- `server/worker.js saveScore/events/draftTour`: проверка Telegram initData есть, но клиентские XP/трофеи/события win/состояние over остаются источниками наград/рейтинга.
- Таблицы `payment_receipts` и `purchases` уже существуют; **не заменять и не обнулять** их.

## Новая модель данных
SQL-предложение: `docs/economy-schema-proposal.sql` (прошло проверку SQLite in-memory; пока НЕ миграция для production).
- `econ_accounts`: server coins, trophies, authority, version.
- `econ_inventory`: lifetime owned_total/consumed_total на каждую карту; available = own-used. Без отрицательного остатка.
- `econ_entitlements`: уникальные перманентные права (скины, premium pass, бонусы).
- `econ_actions`: идемпотентность по (uid, action_id), хеш запроса и сохранённый ответ. Повтор операции с тем же ID и другим телом должен отвергаться.
- `econ_ledger`: журнал изменений с FK к действиям. Для двух одинаковых карт, выданных одной операцией, нужна **одна** строка (asset_type, asset_key) c delta=2.
- `econ_migrations`: происхождение legacy снимка, хеш, решения о проверке и время импорта.
- `econ_seasons`: серверные XP пропуска; отдельные ключи для наград сезона.

Операции должны быть атомарными: создать запись о действии, условно изменить кошелёк/инвентарь и записать журнал одной SQL-транзакцией. D1 `batch` требует проверки на staging. Для двух получателей подарка списание и зачисление должны быть одной транзакцией, а отказы — без побочных записей.

## API, который надо реализовать
- `GET/POST /economy/state` (подписанный initData, серверные balances/version/entitlements/inventory).
- `POST /economy/action`: `actionId`, разрешённый тип, whitelisted параметры, серверная проверка условий; запрет произвольных `coinsDelta`/`cards`.
- `POST /economy/pack/open`: сервер выбирает содержимое по валидному источнику открываемого пака, выдаёт результат **до** анимации.
- `POST /economy/club/donate`: членство, собственная свободная копия карты, request лимит, условное списание/зачисление, idempotency.
- `POST /economy/claim`: проверка условия дороги трофеев/пропуска/сезонной награды в D1; уникальный ключ claim.
- `POST /economy/migration/preview`: только предварительный снимок. Не доверять присланным активам как гарантированно честным.
- Админ-инструменты для повторной выдачи подтверждённых Stars покупок и расследования расхождений (не открывать массовую выдачу пользователям).

## Поэтапный перенос, чтобы не потерять данные

### Этап A — подготовка
1. Снять **настоящий бэкап production D1** и проверить восстановление в staging.
2. Изучить сохранения с согласия пользователей и без секретов/личных данных в логах.
3. Снять baseline: расхождения `saves`, `ustats`, `purchases`, `payment_receipts`, число владельцев карточек.
4. Сделать таблицу действующих предметов/цен/типов карточек и единый `economyCatalog`; версии каталогов сохраняются в транзакциях.
5. Не выключать существующие функции и не менять баланс игроков на этом этапе.

### Этап B — staging в режиме shadow
6. Поднять отдельный staging Worker с отдельной D1 и отдельными тестовыми платежами; применить туда SQL после проверки совместимости.
7. Импортировать доверенные `payment_receipts`/purchases, затем подлинные серверные факты (если существуют).
8. Для legacy сохранений фиксировать снимок и хеш; `localStorage` и Telegram CloudStorage не являются криптографическим доказательством — только вариант восстановления, не источник новой бесконечной валюты.
9. Выявленные расхождения из разных устройств направлять в статус `review`; не выбирать автоматически больший баланс, не удалять прежний оригинал.
10. Shadow-результаты только сравниваются и логируются; UI и существующий кошелёк пока работают как раньше.

### Этап C — реальные транзакции за пределами production
11. Вынести в серверные транзакции: оплаченные Stars товары → монетные покупки → пакеты/случайность → клубные подарки → SBC → награды дороги трофеев/пропуска.
12. Каждая операция получает устойчивый `actionId` до первого запроса, повтор с тем же `actionId` возвращает тот же результат, а не вторую награду.
13. Новые карточки гарантированно выдаются сервером, клиент только проигрывает анимацию; не меняет authoritative баланс напрямую.
14. Не перевести игрока в server-authoritative режим до успешного approved импорта и сверки подтверждённых покупок.

### Этап D — подтверждённое включение
15. После согласования окна релиза, резервной копии и rollback-плана включить feature flag сначала для тестовых аккаунтов, затем небольших групп игроков.
16. Когда `authority = 'server'`, старые `/save` и `Cloud.pull` не должны переписывать `coins`, `cards`, `paid`, `rw.trophies` и `rw.pass` из клиента.
17. При офлайн-режиме использовать только просмотр последнего подтверждённого состояния; выдача/трата ценных наград ждёт интернет.
18. Следить за отказами, повторными действиями, расхождениями, пропавшими покупками и задержками D1; отключать feature flag при регрессиях.
19. После стабилизации перенести рейтинги на проверенные серверные результаты, но не «обнулить» старые рекорды.

### Этап E — игровые победы
20. Отдельно реализовать серверную верификацию матчей/турниров. `state.over` и `event kind:win` — не доказательства результата.
21. Для детерминированного драфта использовать выданный сервером seed, верификацию состава и воспроизведение допустимых действий; для онлайна требуются результаты обоих участников и антифрод.
22. До внедрения верификатора старые события использовать как телеметрию, **не** как повод для ценных серверных выплат.

## Инварианты тестов
- Баланс монет и доступных копий никогда не отрицателен.
- Та же операция (включая повтор после потери ответа и конкурирующие запросы) не выдаёт награду дважды.
- Разные payload под одним `actionId` отвергаются.
- Покупка Telegram Stars засчитывается только после действительного `successful_payment` и строго одному пользователю.
- Срок действия премиум-пропуска и покупки скинов сохраняются при смене устройства.
- Донор не может подарить отсутствующую или потраченную в SBC копию; получатель не теряет доставленную карту при неудачном ack.
- Смена версии каталога не меняет уже начисленные награды или историю чеков.
- Нет уменьшения существующих балансов или потери купленных предметов при миграции.
- После включения server-authority локальные старые сохранения не могут повысить/понизить подтверждённые балансы.
- История `payment_receipts`, `purchases` и `saves` остаётся доступной для сверки.
